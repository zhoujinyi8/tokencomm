# TokCom 阶段 53：TER 返回量与全图误码率口径

本核验在完整冻结汇总后进行，属于事后描述性定义核验，不改变主协议或主结果。核验对象是固定公开提交中的代码返回量，不据此推断论文最终图表采用了何种统计实现。

## 固定代码的返回定义

[作者 GenDecoding 源码](https://github.com/liqiao19/TokenCom_Code/blob/0422ed32dcde3347e0bb6697f343f7a9ff7b3214/Trainer/vit.py#L440)先取最终代码在原掩码内的预测，与原 token 比较，随后返回名为 `TER_af` 的量：

\[
r=\frac{\text{掩码内最终预测正确的 token 数}}{\text{batch size}\times\text{每图 token 数}}.
\]

全图残余误码率则是：

\[
\mathrm{TER}_{\mathrm{whole}}=\frac{\text{全图最终错误 token 数}}{\text{全图 token 数}}.
\]

两者含义不同，不能直接互换。合成接口核验中，四个位置全部被掩码且全部预测错误，实际全图 TER=1，而方法返回 `TER_af=0`。该例在 `w=0/1/9` 三条调用分支均通过，详见 `stage53_cmi_interface_audit.json`。

## 完整冻结集对账

全部 100 图×5 轮共 128,000 个 token。下面的“返回公式值”由已保存最终 token 按源码公式重算，不冒称保存了每次原始函数返回值。所有恢复文件均与原进度清单的 SHA-256 一致，结果与冻结汇总的正确 token 均值一致。

| 路径 | 返回公式值（正确掩码 token/全图） | 实际全图残余 TER |
|---|---:|---:|
| 直接接收解码 | 不适用 | 2.061719% |
| 真值掩码恢复 | 0.821094% | 6.138281% |
| CRC 掩码恢复 | 1.592969% | 13.157031% |

| 恢复路径 | 掩码 token | 掩码前原本正确 | 修复原错误 | 将原正确改错 | 最终错误 token |
|---|---:|---:|---:|---:|---:|
| 真值掩码 | 8,908 | 6,269 | 292 | 5,510 | 7,857 |
| CRC 掩码 | 18,880 | 16,241 | 273 | 14,475 | 16,841 |

直接接收原有 2,639 个错误。两条恢复路径均满足“最终错误＝原错误−修复＋改错”的独立计数恒等式。核验记录见 `runs/stage53_ter_definition_audit.json`。

## 对结果解读的影响

冻结主指标一直使用全图最终 token ID 的精确正确数，没有把上述返回变量当作全图 TER。当前全量结果显示，在本设置下，生成替换会改变许多原本正确但被整包掩码的位置；精确 token 计数与图像质量指标应分别报告。

该核验只说明固定公开源码的变量定义及本次缓存的 token 对账。图像质量的轻微变化不能自动解释为精确 token 误码率改善，也不能据此断言不同版本代码或论文最终统计实现存在相同问题。所有六条冻结路径仍完整报告，三档探索门控不作选择。
